Architecture decision record · consolidated

Device & sensor data architecture

A schema review of the Da Nang traffic platform, four device-payload validations, and the target design: a bounded set of stream shapes, a declarative field manifest, and typed projections replacing attribute search over JSONB.

PostgreSQL 16.14 Scope CadPro TMMS Decisions 38 Status draft for review Date 3 Sep 2026

Section oneSummary

The platform stores every device reading in one JSONB table partitioned by customer and month. Adding a device type is cheap; querying by payload attribute is not. The fix is not more indexing — it is making payload shape a first-class physical dimension, and moving three kinds of data out of the event row that were never event data.

The existing production tables already contain the proof that typed projections work. devicedata_platenumber — a hand-built projection of one payload shape — holds 76% of the same events in 10% of the space.

The five conclusions

  1. Device type is the wrong axis; payload shape is the right one. One AI camera emits detections, traffic counts and health reports. Device types grow with every customer; payload shapes do not — there are eight, and adding a device type adds none.
  2. A declarative field manifest replaces five scattered metadata tables. One declaration per field drives ingest parsing, projection DDL, API filters, the generated UI panel and the Vietnamese labels.
  3. 48% of every detection row is a trajectory blob nobody queries. Moving it to the archive cuts the 2,000-camera NVMe requirement from ~12.4 TB to ~5.2 TB.
  4. Postgres only. Customers run their own on-prem deployments, so a second database server is a support liability. The archive tier is Parquet on the existing NAS, read in-process by DuckDB.
  5. The multi-tenant layer is a design error and a live isolation defect. One deployment per customer means project_code — and the watchlist tables currently shared across customers — should not exist.

Section fourArchitecture

The design rests on one distinction. Device type answers "what is this hardware?" and governs identity, icon, map layer and permissions; it is open-ended and grows with every customer. Stream type answers "what shape is this message?" and governs storage, partitioning, indexes, retention and chart type; it is bounded at eight and adding a device type adds none.

A device's enabled features — not its type — determine which streams it emits, because CadPro devices are smart units with feature toggles and LPR is one of them.

Layer walkthrough

Layer 1 — Registry

Small, typed, foreign-key enforced. object is the sited thing that appears on the map and owns the single authoritative geometry(Point,4326); device is the hardware at that object; device_type is the model. Everything the map draws comes from here, so the map query never touches telemetry. Per-device configuration currently repeated in every event — nva_url_lan, nva_network, the camera description — moves into device.config and is joined.

Capability sits one level down. device_type_feature declares what a model can do; device_feature records what a specific unit has enabled; and device_feature_history is append-only, because if LPR was switched off for three hours then "no violations occurred" and "detection was disabled" produce identical data. That distinction is a question a defence lawyer asks.

Layer 2 — Ingest

devicedata remains an append-only JSONB log, partitioned stream_type → day. No triggers: the write path does nothing but write. The JSONB is kept as the audit and reprocessing payload for the stream's configured retention window, then archived. The trajectory blob never enters this table — the gateway routes it straight to the archive.

Layer 3 — Serving

One typed table per stream, columns generated from the manifest, each partitioned at a grain matched to its rate. These are what every user-facing query reads: error_bitmask is a real int[] with a GIN index, plate is a real text column with a real btree, and no datajson->> appears on the read path. device_state holds exactly one row per device with its latest reading — what the map and the dashboard poll — replacing the per-ping UPDATE public.object and taking that contention off the table the map reads from.

Layer 3b — Mutable workflow

detection_workflow is small by nature: violations are 0.018% of detections, so roughly a million rows a year. It holds review status, reviewing officer, download and sync state, priority and notes — resolving a real contradiction in the current design, where eleven mutable fields live inside an append-only table that cannot be updated at scale.

Layer 4 — Archive

Beyond each stream's hot window, rows are written once to Parquet on the NAS that already exists for video, and read back in-process by DuckDB embedded in the backend. Three domains live there: aged raw JSONB for reprocessing after a manifest change, aged projections for multi-year plate search, and the trajectory tracks, which are archive-only from the moment they arrive.

Why no second database server

ClickHouse would compress this data best and query it fastest. It was rejected because customers run their own on-prem deployments and CadPro does not host them. A second engine means per-site backup, DR, monitoring, upgrades and procurement, debugged remotely at sites the team cannot see, under a three-year support contract. DuckDB is a library, not a server: MIT-licensed, no daemon, no port, nothing for customer IT to operate. Timescale compression (whose licence conditions redistribution on the customer being barred from modifying the schema) and Citus columnar (AGPL) both need legal review and are unnecessary if this holds.

Moving objects — how position reaches the map

A vehicle is a movable object type. The bus or fleet vehicle is the object; the GPS unit is a device attached to it; and the object's location comes from GPS rather than from a survey. The payload confirms the separation is real — Dev.dev_sh is a licence plate (50E-854.78), so the vehicle keeps its identity, route assignments and history when the tracker is swapped.

Positions arrive every 5 seconds, which makes this a high-volume stream rather than a minor one:

Three consequences follow from the 5-second interval. First, stream_position needs daily partitions, not the weekly grain in the DDL above — at 2,000 devices a weekly partition would hold 242M rows. Second, device_state is a small table taking hundreds of upserts per second, which makes its physical design a requirement rather than a tuning detail. Third, the GiST index on stream_position.location becomes the expensive object at this volume — a spatial index over a billion rows a month adds an estimated 60–80 GB/month, so it is worth checking whether geofence and zone queries can be bounded by device and time first and filtered spatially afterwards.

The path of one GPS ping

The bus payload carries two sub-objects, and every value arrives as a string:

Incoming · one message, two streams
{ "Dev":    { "dev_sh": "50E-854.78", "cpu_temp": "34.7", "fw_ver": "1.20", ... },
  "DevMsg": { "gps_lat": "15.948215", "gps_long": "108.220024",
              "gps_speed": "17.71", "gps_course": "333.02",
              "gps_sats": 31, "gps_qual": 1, "gps_status": "A", "dev_static": 0 } }
  1. The gateway fans it out (D14): $.DevMsg to the position stream, $.Dev to the health stream. Two rows in devicedata from one message.
  2. The manifest turns two fields into one column. gps_lat and gps_long are separate source paths combining into a single geometry(Point,4326) — a derived field under D18, with the string-to-numeric coercion declared rather than hardcoded.
  3. The worker appends to stream_position, idempotent on (times, source_id). Every fix is recorded, valid or not.
  4. The worker upserts device_state — the only write the map sees.
The upsert that moves the marker
INSERT INTO device_state AS ds (device_id, last_seen_at, location, speed_kph, online)
VALUES ($device, $times,
        ST_SetSRID(ST_MakePoint($long, $lat), 4326),  -- long first; a lat/long swap is the classic bug
        $speed, true)
ON CONFLICT (device_id) DO UPDATE
   SET last_seen_at = EXCLUDED.last_seen_at,
       location     = EXCLUDED.location,
       speed_kph    = EXCLUDED.speed_kph,
       online       = true
 WHERE ds.last_seen_at < EXCLUDED.last_seen_at;  -- a late packet must not move the marker backwards

That WHERE clause carries more weight than it looks. The worker cursors on id rather than times precisely so late packets are not lost, which means a fix from ninety seconds ago can arrive after a newer one. Without the guard the vehicle jumps back up the road.

⚠ To discuss with the team — this differs from the current implementation

Nothing in this subsection is decided. The current version already implements position updates through a row-level trigger, so these are proposals for review, not agreed changes.

1 · Live position moves out of object. Today trg_devicedata_update_object_location issues an UPDATE public.object on every datapoint carrying coordinates. That makes the table the entire map depends on the hottest write target in the system, and object carries a GiST index on location. The proposal splits the write three ways: devicedata for audit, stream_position for history and playback, device_state for the one row per device that the map reads. For a movable object type, object.location then means depot or home base and is never rewritten by telemetry.

2 · device_state should carry no index but its primary key. This one is counterintuitive and worth arguing about. A Postgres UPDATE writes a new row version, and HOT updates avoid touching indexes only if no indexed column changed. Every ping changes location and last_seen_at. Index either one and every one of those 400 upserts per second writes new index entries and leaves dead ones — relocating the bloat rather than removing it. On a table of a few thousand narrow rows a sequential scan for "every live vehicle in this viewport" is sub-millisecond and beats an index scan anyway. Paired with fillfactor = 70 and per-table aggressive autovacuum, which extends the instinct already present on today's devices table.

3 · A validity gate on gps_status. The current trigger fires whenever latitude, longitude and object_id are non-null. It does not check gps_status, where "A" means an active fix and "V" means void. A void reading still carries coordinate fields — often 0,0 or a stale value — and is written straight to object. Recording every fix in stream_position while advancing device_state only on a valid one means the marker stops moving instead of teleporting, and a stale last_seen_at becomes the offline indicator.

Also worth a decision: whether 5-second resolution needs to persist for the full retention window. It is clearly right for driver-behaviour analysis and trip playback, and almost certainly excessive for three-year reporting — thinning to 30- or 60-second resolution on archive would cut the position tier substantially.

Two position sources, derivable rather than special-cased

Device is…Position comes fromUpdated
On a fixed object — camera, controller, environmental unitobject.locationOnly when someone physically moves and re-surveys it
On a movable object — bus, fleet vehicledevice_state.locationEvery valid fix, every 5 s

Which one applies needs no special case: a device whose enabled features include gps_track emits the position stream, so it is on a movable object. The feature model already answers it.

One frontend consequence: course_deg and speed_kph are not decoration. Even at 5-second intervals a marker that only jumps on each ping reads as broken, so the client interpolates along the last known heading at the last known speed and snaps to the real position when it arrives. dev_static matters for the same reason — a parked vehicle should not be animated, and GPS jitter on a stationary bus is what makes markers vibrate.

Two delimited collections, opposite treatments

Both the camera and the controller hide an array inside a string. nvaevent_data is 1,377 bytes of trajectory that nothing ever filters on, so it becomes an archive blob. CtrlData_LightState is 72 bytes of signal aspects that answer "which intersection had conflicting greens at 14:26", so it becomes a smallint[] with a GIN index — not child rows, which would multiply controller telemetry 36×. Same shape, opposite handling, which is why the manifest declares collection_handling explicitly rather than inferring it.

The trap D25 creates

stream_detection is partitioned by times, so a lookup by id alone cannot prune — it scans all 156 partitions at three-year retention. That is the same failure class as the current 324-second query. The single-id API stays, but the backend must always carry detection_times into the join. This has to be a code-review rule, because it will look redundant to whoever writes the next endpoint.

Section eightProjection worker rules

Non-negotiable. Each one corresponds to a defect found in the current pipeline.

  1. Never read to the head of the table. Guard with xmin < pg_snapshot_xmin(pg_current_snapshot()), or a fixed visibility lag longer than the longest ingest transaction, plus a nightly repair pass over the last 48 hours. Ids commit out of order, so reading to max(id) loses rows permanently and silently.
  2. Cursor on id, never on times. Detections arrive late; a time cursor skips them forever. Bound the read with a recent-time window for partition pruning only, and drop that bound for backfill.
  3. Idempotent write — unique key plus ON CONFLICT DO NOTHING. Note that a unique index on a partitioned table must include every partition key column.
  4. The cursor advances in the same transaction as the insert. Separate them and they will diverge without anyone noticing.
  5. Batches of 2,000–10,000, committed per batch, with a sleep on a short batch. Not 100,000.
  6. One binary, two modes — tail and backfill. No per-customer procedures.
  7. Monitor lag and reconcile. Expose now() - last_source_time and rows behind, alert above five minutes, and reconcile raw against projection counts hourly every night.

Why not CDC or logical decoding

Latency is not the constraint at ~230 rows/second average. A replication slot retains WAL until the consumer acknowledges, so a stuck consumer fills the disk — at a site the team cannot see. Slot synchronisation to a promoted standby arrived only in PostgreSQL 17, and this runs 16.14. Decoding a partitioned table also needs publish_via_partition_root = true. The operational risk buys nothing the batch worker does not already deliver.

Add WAL and backup copies on top. The archive sits on the video NAS, already specified at 100+ TB, so it is effectively free; the expensive column is NVMe. D12 alone reduces the 2,000-camera NVMe requirement from ~12.4 TB to ~5.2 TB.

This table covers cameras only. The position stream is additional and is driven by mobile-device count, not cameras: at 5-second intervals, roughly 43 GB/month for Da Nang's ~400 mobile devices and ~218 GB/month at 2,000. A year of hot positions at the larger figure is ~2.6 TB on its own, which is why the archive-thinning question in Moving objects is a sizing decision and not only a data-fidelity one.
